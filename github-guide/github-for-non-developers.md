# 비개발자를 위한 GitHub — 코드를 몰라도 올릴 수 있는 것

> GitHub는 코드를 올리는 곳이 아니라 **무엇을 왜 바꿨는지가 남는 곳**이다. 코드가 한 줄도 없는 저장소가 많다 — 연구 위키 · 핸드북 · 강의 자료 · 체크리스트 · 프롬프트 · 템플릿. 이 저장소도 파이썬 파일 둘을 빼면 전부 마크다운이다.

## 1 왜 비개발자가 GitHub를 쓰나

- **이력이 남는다** — `보고서_최종_진짜최종.hwp`로는 어디를 왜 바꿨는지 남지 않는다. 커밋은 "무엇을 왜" 한 줄과 함께 바뀐 줄을 남긴다
- **에이전트가 내 파일을 직접 고친다** — AI에게 일을 맡기면 파일이 바뀐다. 무엇이 · 언제 · 왜 바뀌었는지 남기는 장치가 없으면 받아들일지 되돌릴지 판정할 수 없다
- **실력 증명은 말보다 파일이 빠르다** — "AI 실무 잘합니다"보다 작동하는 저장소 하나. 결과물만이 아니라 과정(기획안 · 계획 · 기록)이 함께 올라간다
- **다른 사람이 고쳐 준다** — 오타 · 깨진 링크 · 새 사례를 풀 리퀘스트로 받는다. 바뀐 줄 옆에 의견이 달린다
- **별(star)은 인기가 아니라 저장이다** — 사람들이 "나중에 쓰려고" 눌러 둔다. 그래서 "바로 복붙할 수 있는 파일"이 있어야 별이 쌓인다

## 2 직군별 — 무엇을 올릴 수 있나

| 직군 | 올릴 수 있는 것 | 이 저장소에서 비슷한 것 |
|---|---|---|
| 강사 · 교육 담당 | 커리큘럼 · 실습서 · 체크리스트 · 수강생 워크북 양식 | checklists/ · templates/ |
| 대학원생 · 연구자 | 문헌 정리 양식 · 연구 워크플로 · 코드북 · 재현 자료(공개 데이터) | 01_페인포인트.md → 02_기획안.md → 기록.md의 사슬 |
| 기획자 · PM | 기획서 양식 · 리서치 프레임워크 · 요구 정의 템플릿 | 02_기획안.md · plan.md |
| 디자이너 · 콘텐츠 제작자 | 프롬프트 라이브러리 · 제작 파이프라인 · 검수 체크리스트 | cases/08 · ethics/ |
| 행정 · 법무 · 회계 | 서식 · 점검표 · 절차 매뉴얼(내부 자료는 빼고 형식만) | glossary/의 표 형식 |
| AI 실무자 | 규칙 파일(CLAUDE.md) · 권한 설정 · 검증 스크립트 · 실패 사례 | 이 저장소 전체 |

**올리면 안 되는 것** — 실제 고객 · 학생 자료, 내부 사업계획, 계약서 원문, 개인정보가 든 파일, 비밀번호 · API 키, 실명 · 연락처 · 기관 내부 사정, 유료로 팔 핵심 자산 전체.

## 3 저장소의 모양 — 처음 10초에 답해야 할 다섯 질문

README가 랜딩페이지다. 열자마자 답이 보여야 한다:

1. **이게 뭔가요** — 한 줄
2. **누구에게 필요한가요** — 직군 서너 개
3. **왜 지금 써야 하나요** — 불편 한 문장
4. **어떻게 시작하나요** — 3분 안에 할 수 있는 세 단계
5. **결과물이 어떻게 나오나요** — 예시 파일 링크 · 표 · 스크린샷

구조 예:

```
저장소/
├── README.md          영어(글로벌 유입) — 또는 README.ko.md와 짝
├── README.ko.md       한국어(실무 전환)
├── LICENSE            라이선스 — 없으면 남이 쓸 수 없다
├── CONTRIBUTING.md    보태는 법 · 지켜야 할 것
├── .gitignore         올리지 않을 것
├── templates/         바로 복사해 쓰는 양식
├── examples/          가상 · 공개 예시와 그 결과
└── tools/             있다면 — 설치 없이 도는 작은 스크립트
```

- 이름은 검색어처럼 — `ai-failure-patterns`처럼 소문자 · 하이픈 · 무엇인지 보이게. 사람 이름 · 내부 코드명은 피한다
- 파일 이름에 한글이 있어도 된다 — 다만 git 설정(core.quotepath false)을 해야 깨져 보이지 않는다
- 폴더에 README를 하나씩 — cases/README.md처럼 목차 역할

## 4 커밋 — "무엇을 왜" 한 줄

| 왜가 없는 메시지 | 왜가 있는 메시지 |
|---|---|
| 수정 | 인용에 원문과 쪽수를 붙이는 규칙 추가 — 원문 없는 인용이 되풀이돼서 |
| 최종 | 표 형식 사례 추가 — 표 줄을 건너뛰는 규칙 때문에 놓친 예시가 있어서 |
| CLAUDE.md 수정 | CLAUDE.md에서 "표는 마크다운으로" 삭제 — 지금 모델은 말하지 않아도 그렇게 해서 |

- 작게 자주 — 한 커밋에 한 가지 이유
- 맡기기 전에 커밋 · 끝나면 diff로 보고 커밋
- 메시지 후보는 에이전트에게 받되 **고르는 것은 나**

## 5 공개 전 보안 점검 — 올라간 것은 회수가 어렵다

올리기 전에 한 번, 에이전트에게 이렇게 시킨다(고치지 말고 찾기만):

```text
이 폴더가 공개 저장소로 올라간다고 가정하고, 이것을 악용하려는 사람의 눈으로 검토해줘.
개인정보 · 내부 자료 · 비밀키 · 이메일 · 전화번호 · 기관 내부 사정 · 실명이 드러나는 부분을 파일별로 찾아 위치와 위험한 이유를 목록으로 보여줘. 파일은 고치지 마.
```

- [ ] 커밋 작성자 이메일이 **no-reply 주소**인가(GitHub 설정 → Emails → Keep my email addresses private)
- [ ] 2단계 인증을 켰는가
- [ ] .gitignore가 **첫 커밋 전**에 있었는가 — 한 번 커밋한 비밀값은 목록에 적어도 이력에 남는다. 키가 들어갔다면 지우기보다 **키부터 재발급**
- [ ] 예시 자료는 가상이거나 공개이고 첫 줄에 그렇게 적혀 있는가
- [ ] 특정 개인 · 제품을 비난하는 문장이 없는가

## 6 별을 받는 저장소의 공통점 — 그리고 받지 않아도 되는 이유

- **바로 쓸 수 있는 파일**이 있다 — 양식 · 체크리스트 · 예시. "나중에 써야겠다"가 별이다
- **첫 화면에 결과물**이 보인다 — 표 · 예시 링크 · 스크린샷
- **영어 README + 한국어 README** — 글로벌 노출과 실무 전환을 둘 다
- **업데이트가 보인다** — 커밋 이력 · 변경 기록. 멈춘 저장소는 믿지 않는다
- **문제 한 문장에서 출발**했다 — "AI 챗봇을 만든다"가 아니라 "답변을 받을 때마다 어느 문장을 확인할지 몰라 30분이 걸린다"

별이 적어도 괜찮다 — 저장소의 첫 역할은 **내 변경 이력과 과정을 남기는 것**이다. 남이 보는 것은 그다음이다.

## 7 첫 저장소 만들기 — 순서

1. GitHub 가입 → 2단계 인증 → 이메일 비공개(no-reply 주소 복사)
2. 내 컴퓨터에 Git 설치 확인 → 작성자 이름(GitHub 사용자 이름)과 no-reply 이메일 설정
3. 프로젝트 폴더 **하나에만** 저장소 시작(상위 폴더에 이미 있는지 확인) → .gitignore 먼저 → 첫 커밋
4. 보안 점검(5절) → GitHub에 빈 저장소 만들기(README 없이) → 올리기(push)
5. README를 랜딩페이지처럼 → LICENSE → 공개
6. 이슈 하나를 연다 — 다음에 할 일을 적어 둔다. 문진표(증상 · 기대 · 실제 · 환경 · 해 본 것)가 첫 이슈가 되기 좋다
